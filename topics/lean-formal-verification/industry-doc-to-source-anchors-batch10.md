## 2. 重要校正

### 2.1 Resonate：validator 声明存在，不意味着 checker soundness 证明完成

[valid/lean/correctness.lean](https://github.com/resonatehq/resonate-specification/blob/main/valid/lean/correctness.lean) 文件开头直接说明多数 proof 为 `sorry`；例如 `canon_congruence`、`canon_step` 和 `cone_commute` 仍有 `sorry`。 [valid/lean/real.lean](https://github.com/resonatehq/resonate-specification/blob/main/valid/lean/real.lean) 含特定真实 trace 示例及 tampered variants。因此 `real trace accepted`、某些本地 theorem、任意服务器/验证器 soundness 是三种不同级别的陈述。Batch5/8 只说 trace checker 能“解释”应细化为当前 checker 能跑 **但其理论可信性存在 open proof obligation**。

### 2.2 Lean Kernel Verify：Lean 定义/决策等价和真实 GPU 执行安全分层

- [Bounds.lean](https://github.com/facebookresearch/lean_kernel_verify/blob/main/lean/KV/Spec/Bounds.lean) 有 `holdsPar_eq` 证明 Boolean checker 与形式规格 `Holds` 一致。其输入为 `Run` / Host / KIR events，不能推出与真实 GPU 事件必然一致。
- [TmemReuse.lean](https://github.com/facebookresearch/lean_kernel_verify/blob/main/lean/KV/Spec/TmemReuse.lean) 有 `holdsB_eq`；[StoreReuse.lean](https://github.com/facebookresearch/lean_kernel_verify/blob/main/lean/KV/Spec/StoreReuse.lean) 有 `holdsOnB_eq`。这是模型内布尔判定与规格等价；CTAs、角色完备性、Happens-Before ledger 等前提不可隐藏。
- [NamedBarriers.lean](https://github.com/facebookresearch/lean_kernel_verify/blob/main/lean/KV/Spec/NamedBarriers.lean) 定义 `analyze`/`Holds` 与 undecided 路径；不得由某个输入 PASS 推导无界活性。
- [Check.lean](https://github.com/facebookresearch/lean_kernel_verify/blob/main/lean/KV/Check.lean) 的 `SpecId.Holds` 将 P0/P1 性质路由到实际 Lean 定义，是检查器的统一入口。

### 2.3 Zisk FV：必须根据当前原始源码纠正先前对提取桥接的落后判断

当前上游 [Extraction.lean](https://github.com/eth-act/zisk-fv/blob/main/ZiskFv/Compliance/AeneasBridgeTrust/Extraction.lean) 明确含从跟踪中的 Aeneas `ProductionM2.lean` 导入的 63 opcode 下沉式静态 row-mode pins；[Decode.lean](https://github.com/eth-act/zisk-fv/blob/main/ZiskFv/Compliance/AeneasBridgeTrust/Decode.lean) 有 `zisk_decoder_accepts_supported_shape`、`real_decoder_accepts_in_shape` 等具名证明，而 [Soundness.lean](https://github.com/eth-act/zisk-fv/blob/main/ZiskFv/Soundness.lean) 存在 `root_soundness`。因此不能继续写“主树没有 Aeneas extraction bridge”：更精确的状态是 **SOURCE_PRESENT / BRIDGE_THEOREMS_PRESENT / ROOT_HAS_MODEL_AND_EXTRACTION_TCB**，是否满足端到端原系统假设需要针对 binder/代码版本独立核对，不能靠注释宣称全生产安全或无条件 completeness。历史 Batch6/7 的较早阶段描述应以此增量纠偏。

### 2.4 Sparkle：纯 FSM 证明与可综合 Signal DSL 不自动相连

[Sparkle/Verification/ArbiterProps.lean](https://github.com/Verilean/sparkle/blob/main/Sparkle/Verification/ArbiterProps.lean) 有 `mutual_exclusion`、`no_spurious_grant`、`starvation_free_A/B`、`work_conserving`、`bounded_wait_A/B` 等多条纯状态机性质；[IP/Arbiter/RoundRobin.lean](https://github.com/Verilean/sparkle/blob/main/IP/Arbiter/RoundRobin.lean) 包含可综合 Signal DSL `arbiterSignal` 与 `#synthesizeVerilog`。两者同时存在不等于该 IP 已存在从 Signal 输出到 pure FSM 的逐时刻/状态精化 theorem，也不保证硅片性能或时序约束。
