# TOPIC-018｜Lean 跨行业应用研究框架

> **版本：** v0.1 · Draft  
> **定位：** 本专题的主框架。先回答 Lean 在哪些行业、业务领域和具体问题中可能创造价值，再映射论文、研究成果和 GitHub 项目。  
> **研究顺序：** 行业 → 业务领域/价值链 → 业务场景 → 问题 → 可形式化对象 → 目标性质 → Lean 能力与适配边界 → 论文 → 项目 → 按需审计/原型。  
> **重要边界：** 一般形式化方法在某行业的成功，不等于 Lean 已在该行业落地；存在 Lean 仓库，也不等于存在行业需求或商业机会。

## 1. 核心研究问题

本专题不是建立 Lean 项目名录，而是识别 Lean 作为形式化语言、定理证明器和函数式编程环境，在不同产业与专业领域的可应用位置。

每个方向最终要回答：

1. **谁有问题：** 哪个行业、哪类组织、哪个业务环节或专业群体面临问题？
2. **问题是什么：** 当前依赖人工审查、测试、经验判断、仿真或非形式化数学推导的对象是什么？
3. **为什么值得形式化：** 错误成本、风险、复杂性、复用需求、审计或合规要求是什么？
4. **什么可以被形式化：** 业务规则、数学模型、状态机、算法、程序语义、协议、数据契约或数值误差界？
5. **Lean 能贡献什么：** 定义与规格、定理证明、可执行参考模型、程序验证、精化关系、可复用数学库，还是 AI 生成内容的机器检查？
6. **为什么选择 Lean：** 相比模型检查、SMT、TLA+、Alloy、Dafny、Coq/Rocq、Isabelle 或传统测试，Lean 的增量优势是什么？
7. **如何形成实际价值：** 降低错误与审计成本、提高安全性、缩短验证周期、形成可复用知识资产，还是构成新产品能力？
8. **证据处于什么阶段：** 已有 Lean 生产应用、Lean 研究项目、原型、一般形式化方法行业案例，还是尚待验证的机会假设？

## 2. 总体架构：从行业需求到可验证应用

### 2.1 七层机会分解

| 层级 | 分析对象 | 要回答的问题 | 输出 |
|---|---|---|---|
| L1 行业 | 产业部门、公共服务或专业领域 | 哪些行业存在高价值的可信性问题？ | 行业分类 |
| L2 业务领域/价值链 | 设计、研发、交易、生产、控制、交付、审计、运维 | 问题发生在哪个业务环节？ | 业务领域清单 |
| L3 具体场景 | 一项决策、一个流程、一类系统或一个关键组件 | 谁在什么条件下做什么？ | 场景描述 |
| L4 问题与风险 | 错误、歧义、不一致、不可复现、不可审计、不可证明 | 现有方法的缺口是什么？ | 问题定义与价值假设 |
| L5 可形式化对象 | 定义、规则、状态、算法、模型、数据契约、接口 | 哪些对象能用精确语义表达？ | 形式化对象清单 |
| L6 目标性质与 Lean 能力 | 安全性、活性、正确性、等价性、稳定性、误差界等 | 要证明什么，Lean 在其中承担哪一段？ | Lean 技术路线 |
| L7 证据与落地链 | 理论/标准 → 论文 → Lean/相邻项目 → 原型 → 集成 | 现有工作到哪一步，下一步缺什么？ | 论文—项目映射与验证路线 |

**不允许跳层：** 不能从一个 GitHub 仓库直接推断行业机会；也不能从行业有形式化方法案例直接推断 Lean 已经采用。必须能从业务问题追溯到形式化对象，再说明 Lean 的作用。

### 2.2 纵向行业与横向能力

本框架采用双轴结构：

- **纵轴：行业与业务场景。** 说明需求来自哪里、谁会使用、价值在哪里。
- **横轴：跨行业问题类型与形式化能力。** 说明同一种 Lean 方法如何复用于多个行业。

例如，“状态机不变量”既可用于交易订单、支付清算，也可用于航空控制、工业机器人和分布式共识；不能因此把这些行业合并成一个行业。

### 3.1 分类使用规则

- 行业是需求入口，研究方向是专业问题入口；两者不能混用。
- 一个应用机会可以跨多个行业，但要分别写出各行业的具体场景，不可只写“适用于所有行业”。
- 数学、逻辑、软件语义、概率统计、信息论、优化控制、数值分析、密码学等主要是**横向专业领域/能力域**，不应全部与行业并列。
- 同一行业内可以有多个完全不同的形式化对象；同一种形式化方法也可以跨行业复用。

## 5. Lean 能力与应用模式

Lean 不应被描述成单一的“证明工具”。它在应用架构中可能承担不同角色：

| Lean 能力 | 主要产物 | 适用问题 | 不自动保证的内容 |
|---|---|---|---|
| 形式化定义与类型系统 | 领域类型、数据结构、精确规格 | 概念歧义、接口契约、单位/维度约束 | 定义是否忠实于真实业务 |
| 定理证明与 Kernel 检查 | 可由 Kernel 检查的证明项 | 数学定理、不变量、算法性质 | 前提是否符合现实 |
| 可执行参考模型 | 规格模型、参考解释器、判定函数 | 规则引擎、策略、协议、算法 | 生产实现自动等价于模型 |
| 程序验证与精化 | 程序规格、抽取模型、精化证明 | 关键函数、编译器、密码学实现 | 未覆盖代码路径或外部环境 |
| 可复用数学库 | 领域定义、定理、结构和引理 | 数学密集型行业、重复证明 | 领域模型本身完备 |
| 元编程与自动化 | tactic、检查器、证明生成工具 | 大规模证明义务、重复性证明 | 自动生成结果未经 Kernel 检查 |
| 可信计算与证书检查 | 可检查证书、受限计算证明 | 优化、数值、SAT/SMT 结果的可信接口 | 外部求解器全部过程都可信 |
| 形式化知识资产 | 机器可读定理、依赖图、可检索声明 | 科研、教育、知识服务、AI for Math | 自然语言来源和形式化翻译必然正确 |

### 5.1 典型集成模式

1. **Lean 作为规格层：** 先形式化业务规则和系统不变量，现有 Rust/Python/C++/RTL 继续负责生产执行。
2. **Lean 作为证明层：** 对数学模型、算法和关键逻辑证明性质，外部系统负责数据、仿真和运行。
3. **Lean 作为参考实现：** 建立可执行模型，与生产实现做差分测试；如需强保证，进一步建立 refinement/semantic-preservation 证明。
4. **Lean 作为验证内核：** 外部 AI、搜索器或 SMT 生成候选证明/证书，Lean Kernel 或明确的 checker 负责最终检查。
5. **Lean 作为知识基础设施：** 把论文、标准和领域理论中的精确结果组织成可复用库，支撑后续研究和工程验证。

## 6. Lean 适配性判断：什么时候值得用，什么时候不该硬用

### 6.1 高适配特征

- 关键规则、模型或算法可以被精确表达。
- 需要的是逻辑保证、数学保证或明确条件下的性质，而不只是经验上“测试没发现问题”。
- 错误代价高，或同一规格会被多个团队/系统重复使用。
- 问题可以分解成可组合的定义、引理和不变量。
- 有可建立的模型—实现接口，例如精化、代码生成、抽取、差分测试或受限输入域。
- 能接受前期形式化成本，并有维护证明的责任主体。

### 6.2 低适配或必须混合其他方法的特征

- 需求本身含糊、不断变化，尚不能形成稳定规格。
- 目标主要是判断现实世界的经验事实，例如市场收益、临床疗效或物理参数是否真实。
- 核心风险来自数据质量、采样偏差、分布漂移或模型失配，而不是逻辑推导。
- 需要对超大状态空间进行穷举探索，且模型检查器比交互式定理证明更直接。
- 证明成本显著超过可预期的风险降低，且不存在复用价值。
- 运行性能、外部设备、传感器、人的行为或环境扰动是主要不确定性。

### 6.3 Lean 与相邻技术的选择关系

| 技术 | 更适合的任务 | 与 Lean 的关系 |
|---|---|---|
| Lean | 数学密集、需要可复用定理、精确规格、证明对象和可信 Kernel 检查 | 本专题重点研究对象 |
| TLA+/PlusCal | 并发、分布式系统、时序状态规格与模型检查 | 可先探索状态空间，再将关键不变量或数学性质形式化 |
| Alloy | 关系结构建模、有限范围反例探索 | 可用于早期设计探索；不等同于 Lean 证明 |
| SMT/SAT | 可判定逻辑片段、位向量、算术和约束求解 | 可作为 Lean tactic/证书生成的后端，需审计信任边界 |
| Dafny/F*/Coq/Rocq/Isabelle | 程序验证、类型化规格、证明和不同生态的工程集成 | 作为方案比较对象，不预设 Lean 一定最优 |
| 抽象解释/静态分析 | 大型程序的近似安全属性分析 | 与定理证明互补 |
| 属性测试/差分测试 | 大量输入下比较行为、发现实现偏差 | 是测试证据；不能自动升级为数学证明 |
| 仿真/数字孪生/实验 | 物理、工程和经验系统的行为评估 | 验证模型与现实的差距；Lean 不能替代实验 |

**选择原则：** 研究对象决定方法，不为使用 Lean 而使用 Lean。允许结论是“该问题更适合 TLA+、SMT、模型检查或统计验证，Lean 只承担局部证明”。

## 7. 机会价值与落地成熟度

### 7.1 机会评价维度

每个候选机会在进入论文和项目映射前，先按以下维度描述；首版不预设分数，避免在缺少行业证据时制造伪精确排名。

| 维度 | 核心问题 |
|---|---|
| 业务重要性 | 错误会造成多少安全、财务、合规、运营或声誉损失？ |
| 形式化清晰度 | 需求、规则、状态、算法和假设能否精确表达？ |
| Lean 增量价值 | Lean 是否比现有工具带来更强的数学复用、证明可信性或规格—实现连接？ |
| 复用范围 | 同一证明/规格能否跨版本、产品、组织或行业复用？ |
| 工程桥接 | 能否连接现有代码、数据、仿真、硬件或工作流？ |
| 维护成本 | 规格和证明在业务变化时如何维护？需要什么专业团队？ |
| 验证边界 | 哪些现实假设、数据质量和实现路径仍需其他证据？ |
| 采用条件 | 是否存在标准、监管、采购、安全审计或客户需求推动采用？ |

### 7.2 证据成熟度分级

必须区分 Lean 专属证据与一般形式化方法证据：

- **L-PROD：Lean 生产工作流。** 有组织、产品或生产流程的公开证据，能说明 Lean 在实际研发/交付中承担的职责。
- **L-RESEARCH：Lean 研究成果。** 有论文、固定代码或可回读的 Lean 研究项目，但不代表生产部署。
- **L-POC：Lean 原型。** 有可运行/可检查的最小示例或概念验证，范围有限。
- **FM-INDUSTRY：一般形式化方法行业证据。** 该行业使用了形式化方法，但所用工具不一定是 Lean。
- **HYPOTHESIS：应用假设。** 从业务问题和 Lean 能力推导出的潜在机会，尚无直接应用证据。
- **NO-EVIDENCE：本轮未找到足够证据。** 不是证明该方向没有机会。

示例：AWS Cedar 是 Lean 生产验证工作流的直接案例；铁路、航空、汽车、医疗、光刻制造等行业存在一般形式化方法应用证据，但不能因此标成 Lean 生产应用。Lean 官方 Use Cases 页面还列出 Aeneas、ArkLib 和 Veil 等不同类型的研究/工程案例。具体分类和边界以来源为准。

## 8. 从机会到论文、项目和原型的标准路径

只有完成行业机会的初步定义后，才进入下游资源映射：

1. **机会定义：** 确定行业、业务领域、参与者、流程、痛点和价值假设。
2. **形式化分析：** 明确对象、语义、输入输出、假设、目标性质和反例类型。
3. **文献检索：** 先查行业标准、原始理论、综述、正式论文和技术报告；分清行业需求证据与 Lean 方法证据。
4. **方法匹配：** 判断 Lean、模型检查、SMT、静态分析、测试或混合方法的合理分工。
5. **论文映射：** 将每篇论文关联到具体问题、形式化对象、方法和研究限制。
6. **项目映射：** 只找与该问题/论文直接相关的 Lean 项目；相邻工具单独标记，不冒充 Lean 实现。
7. **按需项目审计：** 当方向进入优先研究、复用或原型阶段时，再固定 commit，检查许可证、工具链、依赖、关键声明、证明状态、构建和 CI。
8. **原型验证：** 选择一个可控业务子问题，建立 Lean 规格/证明和实际系统之间的桥接。
9. **应用评估：** 比较传统方案与形式化方案的成本、错误发现、复用性、维护性和业务收益。

### 8.1 明确禁止的倒置路径

- 不从 GitHub 热门仓库列表反推行业机会。
- 不以项目数量或 star 数量作为应用价值。
- 不把一般形式化方法论文中的工具说成 Lean。
- 不因 Lean theorem 通过就宣称现实系统正确。
- 不把数学定理、程序实现、数据来源、经验效果和商业价值合并成一个“已验证”状态。

## 11. 主要来源锚点

以下来源用于建立行业范围和方法边界。它们的证据层级不同，不能互相替代：

1. [Lean 官方 Use Cases](https://lean-lang.org/use-cases/)：Lean 专属案例，包括 Cedar、Aeneas、ArkLib、Veil 和 Mathlib。
2. [Lean 官方 Cedar 案例](https://lean-lang.org/use-cases/cedar/)：AWS 使用 Lean 建立可执行模型、证明关键性质，并通过差分测试连接 Rust 生产实现。
3. [Formal Methods in Industry](https://doi.org/10.1145/3689374)：跨行业形式化方法综述，覆盖铁路、汽车、航空、操作系统、云服务/电商、硬件设计、光刻制造和移动设备；这是一般形式化方法行业证据，不是 Lean 采用清单。
4. [NASA NTRS：Formal Methods at NASA: Past, Present, and Future](https://ntrs.nasa.gov/citations/20250006044)：列出软件、硬件、Web 服务、分布式数据库、交通、通信、核能、金融和医疗等应用领域，并讨论 AI/ML、机器人和网络物理系统的潜在方向。
5. [DARPA Formal Methods Examples](https://www.darpa.mil/research/research-spotlights/formal-methods/examples)：介绍形式化方法的收益、成本和案例，包括 parser、seL4 与 AADL；强调形式化方法的适用性与工程门槛。
6. [Lean Community Project Registry](https://leanprover-community.github.io/lean_projects.html)：作为后续寻找数学及相邻领域 Lean 项目的资源入口，不作为行业机会分类的替代。

## 12. 当前结论与限制

本文件建立的是**研究架构 v0.1**，不是完整行业调研，也不是商业机会排名。行业列表是覆盖骨架；每个细分机会的市场规模、付费主体、竞争方案、实施成本和实际 Lean 项目仍需在后续选定方向后核实。当前阶段不开展大批 GitHub 项目审计。

 
## 13. 用户明确的递归下钻与 GitHub 叶节点要求（2026-11-23）

此前的“七层机会分解”是分析视角，不是固定深度上限。实际行业树必须按业务复杂度递归：

`L1 行业 → L2 业务领域 → L3 细分领域 → L4 价值链环节/场景 → L5 具体问题 → L6 形式化对象与目标性质 → 论文/标准 → GitHub 项目`

### 13.1 研究叶节点的强制终点

每条最终分支必须到达至少一个真实 GitHub 项目，同时挂接对应论文、标准或原始技术资料。项目类型必须标记：

- `DIRECT_LEAN_APPLICATION`：Lean 已用于具体应用或研发流程。
- `DIRECT_LEAN_RESEARCH`：Lean 直接形式化该领域问题。
- `LEAN_INFRASTRUCTURE`：Lean 基础库/证明工具，支撑领域形式化但不代表行业采用。
- `ADJACENT_FORMAL_TOOL`：Coq/Rocq、F*、TLA+、SPIN、SMT、模型检查等相邻工具。
- `DOMAIN_REFERENCE_IMPLEMENTATION`：行业真实系统/算法/数据模型，作为后续形式化对象，不提供形式化证明。

没有直接 Lean 项目时，不得编造 Lean 采用案例；必须寻找同一问题的相邻形式化项目或真实行业实现，并标记 Lean 直接证据缺失。不能只列论文而不落到 GitHub 仓库。

### 13.2 叶节点停止条件

只有同时具备以下字段，才可以称为“已下钻到项目级”：业务主体/具体场景；独立问题陈述；形式化对象、关键假设和目标性质；对应论文/标准/原始资料；至少一个可回读 GitHub 仓库与关系标签；Lean 作用和未证明的现实假设。

### 13.3 当前主线与范围

- 当前主线是完成全行业递归下钻和论文—GitHub 项目映射。
- 项目源码审计、clean build、最小原型和生产集成不是当前必做步骤。
- 用户可在项目映射完成后挑选需要审计的项目；原型阶段另行评审。
- 首版 60 个叶节点见 [industry-leaf-project-map.md](industry-leaf-project-map.md)，可继续扩展和细化。
