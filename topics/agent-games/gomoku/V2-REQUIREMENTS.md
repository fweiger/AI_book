# AI_book 五子棋｜V2 需求说明：双网页版 AI 固定提示词与跨对局复用

- 研究对象：`fweiger/AI_book` 的五子棋多 Agent 协作实验。
- 本文件性质：**下一版需求/验收标准**。当前已经实现“固定提示词入口 + 活动棋局注册表 + GAME-001 归档 + 按活动 Issue 的裁判路由/终局清空”。已创建并激活 GAME-002 独立空棋盘，但**通用自动开局器和网页版 AI 事件唤醒尚未实现；真实 GAME-002 全局对弈尚未验收**。
- 依据：[GAME-001 验收与结果记录](results/GAME-001-ACCEPTANCE.md)。GAME-001 已 `finished`，白方胜，共 30 手，其中 1～3 手属于人工联调测试。
- 总目标：固定两个独立网页版 AI 的角色提示词；以后每一轮/每一盘无须人为编辑“这是第几步”“最新落点在哪里”“下棋用哪个 Issue”。

## 1. 不变的系统边界

**棋手 A/B 是两个用户分别操作、各自连接 GitHub 的网页版 AI 会话**，不是 Ubuntu 上的两个模型程序，不通过 GitHub Actions 直接调用任何大模型 API。

```text
用户唤醒网页版黑方或白方 AI
  → 固定角色提示词读取 games/active.json
  → 根据 active_game 读取对应 state.json + Issue 评论
  → AI 独立判断（只执行一手）
  → Issue 提交一行 MOVE 身份码 坐标
  → GitHub Actions / Python 裁判验证并写入 state.json、刷新 Issue
  → 用户唤醒另一网页版 AI（如已结束，则双方停止）
```

Ubuntu / 北京服务器如果使用，也**只能作为临时的 GitHub 状态监测或裁判故障补触发**。监测器不得推断棋步、不得评论代下、不得调用 Codex CLI 或任何其他模型，也不得安装为常驻服务，除非用户日后另外授权。

## 2. 稳定的角色提示词（已建立）

- [黑方 AI-A 固定提示词](prompts/AI-A-black.md)
- [白方 AI-B 固定提示词](prompts/AI-B-white.md)
- [GAME-001 的两份历史提示词](prompts/archive/) 与新模板相互独立；历史棋谱不改。

固定模板应在任何轮次原样可用，不在文本中硬编码：
- 当前 `game_id`、Issue 编号、棋盘文件路径或棋手身份码；
- 当前棋局版本、最新步数、最新坐标、下一手目标坐标；
- 来自旧会话记忆的“目前轮到谁”。

唯一长期固定的信息是仓库、注册表文件、角色（黑或白）、规则及落子操作规范。

## 3. 单一活动对局注册表（文件已建立，开局切换待实现）

路径：`games/active.json`

- `schema_version`：注册表版本。
- `active_game`：无活动对局为 `null`；开局时才填 `{game_id,issue_number,state_path}`。
- `last_completed`：最近已结束棋局的只读摘要，不是继续落子的依据。

**最新已启用**：`active_game` 指向独立 [GAME-002 Issue #25](https://github.com/fweiger/AI_book/issues/25) 与 [空棋盘](games/GAME-002/state.json)，开始时版本 0、黑方先手；`last_completed` 仍为 GAME-001。所有后续步数/轮次由 GitHub 实时数据决定。

每局开局须先创建独立 Issue、新 `state.json` 和独立身份码，验证裁判支持游戏与 Issue 绑定，再将 `active_game` 指向新对局。GAME-002 已按此顺序初始化，不允许将旧 Issue #24 直接当新棋局入口，也不允许重置 GAME-001 JSON。

单一活动对局的裁判动态路由已经完成并经离线模拟测试验证：`referee.py` 根据 `active.json` 校验 `game_id / issue_number / state_path`，非本局 Issue 跳过；终局更新 Issue 后清空注册表。**目前不支持同时并行多局，也未完成通用一键开局器；GAME-002 真正从零盘落子仍待用户启动双网页版 AI 验收。**

## 4. 棋谱字段与步数推断（V1 已支持）

每个接受的合法落子都保留：
- `moves[].number`：第几手（从 1 开始连续递增）；
- `moves[].side`：`black` / `white`；
- `moves[].coord`：落子位置，如 `H8`；
- `moves[].comment_id`：对应 GitHub 评论 ID（定位、审计、去重）；
- `state.version`：当前棋局有效提交版本；V1 每接受一手加一。

当前已完成步数 = `len(moves)`，应走步数 = `len(moves)+1`；最新落点是 `moves[-1].coord`（若没有合法落子则为空）。验证 `version == len(moves)`、`moves[].number` 连续；若不一致就停止、不猜测。

**V2 不需要为了记录步数而更改稳定的 V1 MOVE 语法。** 现在仍为 `MOVE <身份码> <坐标>`；步数由裁判基于权威状态自动写入 JSON，AI 无需手动拼接“第 N 步”。

若未来要做乐观锁或多棋局并行，可再评估包含 `game_id`、`expected_version` 的新协议；**未经裁判实现和兼容性测试，不允许让棋手先发送新语法**。

## 5. 严格执行条件（下一盘验收时必须测）

1. **当前状态**：从 `active.json` 获取唯一活动棋局；为 `null`、格式不一致、读取异常即停止。
2. **角色**：权威 `status = playing` 且 `turn` 与棋手颜色匹配；`finished` 后不得发表评论。
3. **未处理评论**：比对 Issue 评论与 `processed_comment_ids`、本人身份码；若已有未处理 `MOVE`，不得重复提交。
4. **真实落点**：AI 自主判断攻守与合法空位；不能由监控程序或提示词提供固定坐标。
5. **防旧状态**：提交前再次读取活动对局注册表、棋盘和必要评论；版本、当前角色或空位变化则放弃旧选择。Python 裁判继续作为最终防并发边界。
6. **提交方式**：只能对当前 Issue 发一条符合既定格式的评论；AI 不修改 `state.json`、注册表、Issue 正文、历史棋谱或裁判。
7. **结束条件**：五连/平局后裁判写 `finished`，双方模板再次被触发时不落子。必须由开局/结局管理流程将 `active_game` 置空并保存最近结果。
8. **身份边界**：公开身份码是棋手标签，不是安全认证；同一 GitHub 作者并不能识别实际上是谁在网页会话中决策。V2 若要求可信身份归因，需要独立设计。

## 6. 任务交接与 UI

- Issue 正文显示最新步数、颜色、坐标、胜负状态，并展示当前应该执行哪一个固定提示词的链接。
- 裁判接受评论后，下一位**网页版 AI 的任务应当可从 GitHub 状态自行推导**，无需用户重写提示词。
- **区别“裁判已接受”与“已自动唤醒另一网页版 AI”。** GitHub `issue_comment.created` 只能启动 Actions，普通网页版 AI 仍需用户手动唤醒，直到产品真实支持相应事件触发。
- GitHub Pages 如已发布只负责展示棋盘/回放，不负责运行棋手模型。

## 8. 非目标与禁止行为

- 不把 GAME-001 的测试落子当作两个 AI 真实决策的数据样本。
- 仅在用户允许从空盘开始时创建独立新局；**不为机器人选择棋步**、不使用模型 API。GAME-002 的激活已得到用户同意。
- 不为了模拟自动交接擅自创建 Ubuntu systemd 常驻服务。
- 不改写 GAME-001 最终 `state.json`、`moves`、`events`。
- 不对“自动唤醒网页版 AI”“GitHub Pages 已发布”“多棋局裁判已可运行”做未经验证的承诺。
